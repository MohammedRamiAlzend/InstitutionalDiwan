# الخطة — الوضع التعليمي (دليل الشرح داخل الواجهة)

**الحالة:** مسودة بانتظار الاعتماد — لم يبدأ التنفيذ.
**النطاق:** واجهة SPA (`institutionaldiwan.front`) فقط. لا تعديل على `InstitutionalDiwan.Server` ولا على قاعدة البيانات.
**آخر مراجعة:** 2026-11-01.
**مرجع الأسلوب:** [plans/module-06-attachments-frontend.md](module-06-attachments-frontend.md) — نفس بنية الأقسام والمراحل ومعايير التحقق.

## 1. الوضع الحالي المؤكَّد (تم فحصه)

**التفضيلات الحالية داخل «إعدادات العرض»** تعمل جميعها على النمط نفسه:

| التفضيل | وحدة التخزين | السمة على `<html>` | الحقل في `SettingsDialog` |
| --- | --- | --- | --- |
| السمة (فاتح/داكن/تلقائي) | `diwan.theme` | `data-theme` | `shared/lib/theme.ts` + خطّاف `useTheme` |
| الكثافة | `diwan.density` | `data-density` | `widgets/app-shell/model/density.ts` |
| الحركات | `diwan.motion` | `data-motion` | `widgets/app-shell/model/motion.ts` |

- `AppShell.tsx` يملك الحالة، يطبّقها في `useEffect`، ويعرض مفتاح «إيقاف/تفعيل الحركات» في قائمة الصدفة أيضًا؛ `SettingsDialog.tsx` يبني كل مجموعة بـ `<fieldset>` + أزرار `aria-pressed`.
- `index.html` يحسم السمة والكثافة والحركات قبل الرسم الأول من `localStorage`.
- لا يوجد حاليًا **أي** ميزة شرح أو جولة أو تلميح: لا `tooltip.tsx` ولا `popover.tsx` في `shared/ui`، ولا حزمة Radix للـ popover (الموجود: checkbox، context-menu، dialog، dropdown-menu، select).
- مصفوفات العناصر التفاعلية لكل صفحة جاهزة وموثّقة في READMEs الخاصة بها، وهي المرجع لكتابة المحتوى.
- الجداول كلها تمرّ عبر `shared/ui/data-table.tsx` (تستقبل `tableId`، وشريط أدوات موحّد: بحث، «الأعمدة»، «صفوف في الصفحة»، تحديث، قوائم سياق الصف/الرأس/الفراغ). **إذًا شرح أدوات الجدول يُكتب مرة واحدة وينتفع به 11 جدولًا.**
- الحقول كلها تمرّ عبر `shared/ui/form-field.tsx` (`label` + متحكّم + رسالة خطأ عربية) — نقطة إلصاق واحدة لشرح الحقول.
- عناوين الصفحات عبر `shared/ui/page-header.tsx` (`title`, `description`, `actions`, `badge`) — نقطة إلصاق واحدة لزر «شرح الصفحة».
- **الأقسام حاليًا JSX بلا هويّات**: لا `id` ولا `data-*` على `<section>`/`<div>` في الصفحات. المقابض المستقرة الوحيدة: `tableId` في كل جدول، و`aria-label` على `role="tablist"` (الوثائق، الحركات، الترقيم، التدقيق، تبويبات الوثيقة)، و`role="group" aria-label="طريقة عرض الأقسام"`.
- **الصرامة في الأذونات**: العناصر المحجوبة بصلاحية **تغيب عن DOM** (وليس فقط معطّلة) عبر `features/auth/ui/RequirePermission.tsx` أو `useSessionStore((s) => s.hasPermission(...))` داخل الـ widget. الاستثناء الوحيد: `InstitutionSettingsForm` يعطّل `EmployeePicker` بدل إخفائه. **أي محتوى شرح يُبنى بالبحث في DOM سيختلف عن الواقع؛ لذا يجب أن يُبنى من نفس شرط العرض الذي يرسم العنصر.**
- لا ماضٍ اختباري للواجهة: `package.json` فيه `dev`/`build`/`lint`/`preview` فقط. البوابات-front هي `npm run lint` و`npm run build` (الذي يشغّل `tsc -b`).
- الخوادم أثناء التطوير: Vite على 5173/5174، وAPI على 5028. التحقق البصري يتطلب دخول المستخدم يدويًا في المتصفح داخل التطبيق (لا نكتب بيانات اعتماد في أي سكربت).

## 2. الثغرات المكتشفة (أساس الخطة)

1. لا وجود لوضع تعليمي أصلاً: المستخدم الجديد يقابل 12 مسارًا و11 جدولًا و6 تبويبات في صفحة الوثيقة وحوارات كثيرة بلا أي شرح داخل التطبيق؛ الشرح موجود فقط في markdown لا يفتحه المستخدم أثناء العمل.
2. لا آلية إلصاق: لا هويّات على الأقسام، فأي «جولة» تشير إلى عنصر يجب أن تبني هذه الهويّات أولًا.
3. لا primitive للشرح: لا tooltip ولا popover، والخيار يجب أن يوائم طلب المستخدم («مربعات حوارية وشرح لكل تفصيلة»).
4. لا سجل مركزي لنصوص الشرح: كتابتها مبعثرة في الصفحات ستجعل المراجعة والاستقرار والتغطية المستحيلة لاحقًا.
5. حساسية الأدوار: شرح زر لا يراه الموظف العادي يخلق معلومة خاطئة، بل مشكلة أمن-معلوماتي صغيرة (الإفصاح عن وجود وظيفة لا يملكها المستخدم).
6. لا ضمانة اتساق: مع ~120 مدخلًا نصيًا، يجب فحص أن كل `guideId` مستخدم في JSX له مدخل، وأن كل مدخل يُستخدم فعلًا.

## 3. قرارات معمارية

### 3.1 التفضيل: `diwan.tutorial` في `shared/lib`، لا في `widgets/app-shell`

الوحدات المكوِّنة للشرح يجب أن يقرأها `shared/ui/data-table.tsx` و`form-field.tsx`، وهما أدنى من `widgets`. وضع الحالة في `app-shell/model` سيخلق استيرادًا للأعلى (ممنوع في FSD). لذلك تُقلَّد بنية `theme.ts` لا `motion.ts`:

`src/shared/lib/tutorial.ts`
```ts
export type Tutorial = 'on' | 'off'
// getStoredTutorial() / applyTutorial(t) → <html data-tutorial>
// setTutorial(t) → localStorage + apply + emit
// useTutorial(): Tutorial  ← useSyncExternalStore، يقرأه أي مستوى
```
الافتراضي `off`: الوضع التعليمي قرار مقصود من المستخدم، لا استجابة لنظام التشغيل (بخلاف `motion` التي تحترم `prefers-reduced-motion`). `index.html` يحسمه قبل الرسم الأول مثل الآخرين، كي لا تظهر/تختفي أزرار الشرح بعد الترطيب.

### 3.2 العرض: رقاقة «؟» + مربع حواري مبنيان على `Dialog` الموجود

- **تحديث 2026-11-02**: العرض الآن عبر `driver.js` (popover مثبّت على المنطقة/الرقاقة + جولة الصفحة بتظليل)، والأنيميشن فيه يبقى مفعّلًا حتى مع «حركات التنقل: متوقفة»؛ التفاصيل في `shared/ui/guide-tour.ts`. ما يلي عن `Dialog` تاريخي.
- **(تاريخي) لا حزمة جديدة**: لا `@radix-ui/react-popover` ولا `driver.js` ولا مكتبة جولات. المطلوب عند المستخدم هو مربعات حوارية، و`Dialog` جاهز ومع عنه أنيميشن فتح/إغلاق واحترام لإيقاف الحركات.
- `GuideChip`: زر أيقونة بحجم صغير (`variant="ghost"`, `size="icon"`, أيقونة `CircleHelp` من lucide) بنص `aria-label="اشرح هذه الأجزاء"`، لا يظهر إطلاقًا عندما `useTutorial() === 'off'`، فيبقى DOM الإنتاجي كما هو حرفيًا.
- `GuideDialog`: `Dialog` بحجم `sm` يعرض `title` + `body` + `note` (المتطلب أو الصلاحية اللازمة إن وُجدت).
- `PageGuideDialog`: نفس الحواري لكنه يعرض مقدمة الصفحة ثم كل مدخل **ظاهر الآن على الشاشة**، مع تنقّل «التالي/السابق» ليعطي إحساس الجولة دون مكتبة. زر فتحه يوضع في `PageHeader actions` عند تمرير خاصية جديدة اختيارية `guideId`.
- **لا Spotlight ولا تعتيم الشاشة**: حجب الصفحة لأخذ إحداثيات عناصر مجهولة الهويّة يحتاج قياسًا ومتابعة تمرير؛ المكاسب توثيقية لا بصرية، والتعقيد لا يبرَّر في المرحلة الأولى. يُذكر كمستقبل في §5.

### 3.3 الإلصاق تصريحي لا اقتباسي: `<GuideRegion id="…">`

بدل البحث في DOM بالمعرّفات، يُغلَّف كل منطِق في الصفحة:
```tsx
<GuideRegion id="users.table">     {/* يرسم children ثم الرقاقة عند الحاجة */}
  <UsersTable … />
</GuideRegion>
```
الفوائد: (أ) العنصر المحجوب بصلاحية لا يُغلَّف أصلاً ⇒ رقائقه لا تظهر، وحواري الصفحة لا يعرضه؛ (ب) لا هويّات `id` جديدة تتصادم مع `htmlFor` القائم؛ (ج) الإزاحة البصرية صفر (`display: contents` في الحالتين). `GuideRegion` يوفّر أيضًا `context`ًا يجعل `PageGuideDialog` يعرف أي مدخلات مرئية حاليًا وبأي ترتيب.

### 3.4 المحتوى: كتالوج ثابت في `shared/config/guides/`، ملف لكل صفحة

الشرح بيانات معرفة مسبقًا بلا منطق، تمامًا كـ `shared/config/routes.ts` و`attachmentLimits.ts` الموجودة. البنية:
```
src/shared/config/guides/
  types.ts      // GuideEntry { id, title, body, note? } و PageGuide { pageId, intro, entryIds }
  common.ts     // مدخلات أدوات الجداول والحقول المشتركة (table.search, table.columns, table.pageSize, table.refresh, table.rowMenu, table.empty)
  users.ts  roles.ts  documents.ts  document-details.ts  movements.ts
  departments.ts  numbering.ts  employees.ts  institution-settings.ts  audit.ts  dashboard.ts
  index.ts      // GUIDES: ReadonlyMap<string, GuideEntry> و PAGE_GUIDES: Record<pageId, PageGuide>
```
قواعد كتابة النص (ثابتة في كل المراحل، ومقياس المراجعة):
- عربية حصرًا،جملة إلى ثلاث جُمل، بلا لقطات شاشة ولا إيماءات وصفية.
- تشرح **الغرض والمتطلبات والأثر**: «ماذا أفعل هنا؟ ومتى؟ وما الذي يتغيّر؟» لا «هذا زر».
- عند اشتراط صلاحية تُذكر الصلاحية باسمها المفهوم («يتطلب صلاحية تسجيل الحركات») لأن المستخدم الذي لا يراها لا يحتاج أن يقرأها أصلًا (§3.5).
- عدم تكرار نصّ الواجهة الحرفي داخل الشرح؛ الإشارة إليه بالاسم.
- لا أرقام هواتف ولا أمثلة بيانات حقيقية ولا إشارات لمسارات داخلية (`Server/…`) في نصوص المستخدم.

### 3.5 الأذونات: المحتوى من مكان العرض، لا من الـ DOM

الرقاقة تُرسم داخل نفس التعبير الشرطي الذي يرسم العنصر:
```tsx
{canCreate && (
  <GuideRegion id="documents.create">
    <Button …>وثيقة جديدة</Button>
  </GuideRegion>
)}
```
فموظف `USER` لا يرى شرح «تسجيل برقم» ولا «إلغاء الوثيقة» ولا تبويب «التصاريح»، ولا يُلمَّح إليها. هذا قرار أمني-سلوكي لا تجميلي، ويُطبَّق في كل صفحة.

### 3.6 حقول النماذج: خاصية `guideId` على `FormField`

`FormField` يضيف `guideId?: string`؛ عند وجوده وتفعيل الوضع تُرسم الرقاقة بعد `label` مباشرة (خارج `<label>` حتى لا تُقرأ كجزء من الاسم). هذا يغطي حوارات: الموظف، القسم، السجل، المستخدم، الدور، رفع ملف، إضافة مشارك/تصريح.

### 3.7 الجداول: خاصية `guideId` على `DataTable` + مدخلات `common.ts`

`DataTable` يضيف `guideId?: string` لشرح الجدول ككل، ويرسم تلقائيًا رقائق `table.search` / `table.columns` / `table.pageSize` / `table.refresh` بجانب أدواتها، ورقاقة `table.rowMenu` عند وجود `rowActions`. النتيجة: 11 جدولًا تُشرح بأربعة أسطر داخل مكوّن واحد، ثم تمرير `guideId` في كل widget (تعديل سطر واحد لكل جدول).

### 3.8 التفاعل مع الحركات والكثافة

- حواريات الشرح ترث `animate-content-in/out` و`animate-overlay-in/out`، فتُفتح وتُغلق كالباقي، وتتوقف عند «حركات التنقل: متوقفة».
- الرقاقات أيقونية بحجم ثابت؛ في الكثافة المريحة تبقى قابلة للضغط (`min touch target` قائم في `Button size="icon"`).
- لا سمة CSS جديدة: لا حاجة لـ `html[data-tutorial]` في الـ stylesheet؛ السمة موجودة فقط لئلا تظهر الرقاقات قبل hydration وتختفي.

### 3.9 ضمانة اتساق: `scripts/check-guide-ids.mjs`

بدون ماضٍ اختباري للواجهة، يُضاف سكربت Node صغير (لا مكتبات) يتحقق وقت البناء/الفحص:
- كل `guideId`/`<GuideRegion id>` ظاهر في `src/**/*.tsx` له مدخل في `GUIDES`.
- لا مدخل يتيماً في `GUIDES` بلا مستخدم (يستثنى ما يصرّح به السكربت).
- لا معرف مكرر، وكل `entryIds` في `PAGE_GUIDES` موجودة، وكل معرّف يبدأ ببادلة صفحته.
يُنفَّذ عبر `npm run check:guides` ويُضاف إلى `lint` كـ`pre` script، فيصبح بوابة خامسة رخيصة مع تزايد المحتوى.

## 4. المراحل

ترتيب المراحل صفحة-صفحة كما طُلب. كل مرحلة تُنتهي ببواباتها وبسweep التوثيق ثم **تتوقف** بانتظار الموافقة على التالية.

### Phase 0 — الأساس: التفضيل + الرقائق + كتالوج مشترك + صفحة واحدة شاهدًا

**الملفات:**
- جديد: `shared/lib/tutorial.ts`، `shared/config/guides/{types,common,index}.ts`، `shared/ui/guide.tsx` (`GuideRegion`, `GuideChip`, `GuideDialog`, `PageGuideDialog`), `scripts/check-guide-ids.mjs`.
- تعديل: `shared/lib/index.ts` (تصدير الوحدة)، `index.html` (حسم `diwan.tutorial` قبل الرسم)، `widgets/app-shell/ui/AppShell.tsx` (حقل + مفتاح قائمة الصدفة «الوضع التعليمي: تشغيل/إيقاف»)، `widgets/app-shell/ui/SettingsDialog.tsx` (fieldset رابع «الوضع التعليمي» بخيارين «مفعّل/متوقف» وفق نمط `motion` تمامًا، مع سطر شرح أسفله)، `shared/ui/page-header.tsx` (`guideId` اختياري)، `shared/ui/form-field.tsx` (`guideId`)، `shared/ui/data-table.tsx` (`guideId` + رقائق الأدوات)، `shared/ui/index.ts`، `package.json` (`check:guides`).
- محتوى `common.ts`: مقدمة مختصرة للوضع + `table.search`، `table.columns`، `table.pageSize`، `table.refresh`، `table.rowMenu`، `table.empty`.

**قبول المرحلة:**
1. مفتاح «الوضع التعليمي» يظهر في «إعدادات العرض» وفي قائمة الصدفة، وحالته تُحفظ لكل متصفح، وتُحسم قبل الرسم الأول، والافتراضي متوقف.
2. في الوضع المتوقف: لا فرق في DOM الإنتاجي عن HEAD الحالي (لا رقاقة، لا عنصر wrapper ظاهر) — يُتحقق بمقارنة `outerHTML` لصفحة المستخدمين قبل/بعد.
3. في الوضع المفعّل: صفحة `/users` وحدها مشروحة بالكامل (Phase 1 تُنقل إليها التفاصيل)، والحوار يفتح ويغلق بحركة، ويتوقف مع «حركات التنقل: متوقفة».
4. `npm run lint`، `npm run build`، `npm run check:guides` نظيفة؛ وبوابتا الـ .NET (build + test) تُشغَّل مرة في نهاية المرحلة بعد إيقاف خادم 5028 التطويري مؤقتًا ثم إعادته.
5. READMEs: `shared/lib`، `shared/config`، `shared/ui`، `widgets/app-shell`، و`institutionaldiwan.front/README.md` و`README.md` الجذرية + سجل هذا الملف.

### Phase 1 — `/users` و `/roles` (كيان الهوية)

**نطاق المحتوى:** ~10 مدخلات للمستخدمين + ~8 للأدوار. تغطي: جدول المستخدمين وأدواته، «مستخدم جديد»، قائمة سياق الصف (تعديل البيانات / إدارة الأدوار / الصلاحيات والإسنادات / إعادة تعيين كلمة المرور)، حوار النموذج بحقولـه، مصفوفة صلاحيات الدور، «دور جديد»، نسخ المعرّفات.
**آلية:** تغليف الأقسام في `UsersPage`/`RolesPage` والـ widgets والحوارات بـ `GuideRegion`، و`guideId` على `FormField`، ومفاتيح `pages/users` و`pages/roles` في `PAGE_GUIDES`، وربط `PageHeader guideId`.
**قبول:** تحقق بصري في متصفحين (مدير، ثم `USER`) بأن الشرح يختفي حيث تختفي الوظيفة؛ البوابات الأربع + `check:guides`؛ توثيق.

### Phase 2 — `/documents` (السجل + الجهات الخارجية)

**نطاق:** ~12 مدخلًا: التبويبان، المرشحات الأربعة (الحالة/الاتجاه/النوع/القسم المالك)، «وثيقة جديدة»، «مسح البحث والمرشحات»، قائمة سياق الصف، «إعادة التحميل»، جدول الجهات الخارجية وحالته وحوار إنشائه/تعديله وحذفه.
**قبول:** كما في Phase 1، مع التحقق من تبويب `?tab=organizations` داخل وضع الشرح.

### Phase 3 — `/documents/:documentId` (أكبر صفحة: تبويبات + إجراءات)

**نطاق:** ~20 مدخلًا موزّعة: رأس الصفحة وإجراءاته الأربعة المشروطة («تعديل المسودة»، «تسجيل برقم»، «إضافة مشارك»، «إلغاء الوثيقة»)، التبويبات الستة («الأرقام» و«التصاريح» مشروطان بصلاحية)، نظرة عامة/الخط الزمني، جدولي الأرقام والحركات والمرفقات والتصاريح وحواراتها (إصدار/إلغاء/استبدال رقم، فتح حركة، رفع ملف، التحقق، الأرشفة، إضافة/إلغاء تصريح).
**قرارات ضمن المرحلة:** الرقائق داخل الحوارات تُستخدم للحقول فقط (`FormField guideId`) لا للأزرار، وإلا صار الحوار شرحًا فوق شرح.
**قبول:** مصفوفة الأدوار كاملة (مدير / `DOCUMENT_EDIT` / قراءة فقط) في الوضعين؛ البوابات؛ توثيق.

### Phase 4 — `/movements` و `/departments`

**نطاق:** الحركات ~8 (صندوقا الوارد/الصادر، مرشحا الحالة/النوع، قائمة سياق الصف، «تحديث الصندوق»). الأقسام ~12 (مبدّل العرض شجرة/مخطط/إحصاء/جدول، البحث ومسحه، «إظهار فروع الموظفين» المشروط، «توسيع الكل/طي الكل»، قائمة سياق العقدة، «قسم جديد»، جدولي الأقسام والموظفين، حوار تفاصيل القسم وموظف، توزيع الأقسام حسب النوع).
**قبول:** التحقق من أن مبدّل العرض وشرح المخطط يظهران فيوضع الشرح فقط، ومن أن شرح «إظهار فروع الموظفين» غائب حين `canViewEmployees === false`؛ البوابات؛ توثيق.

### Phase 5 — `/numbering`، `/employees`، `/institution-settings`

**نطاق:** الترقيم ~12 (تبويبا السجلات/سجل الدوائر، المرشحات بما فيها سنة الترقيم، «سجل جديد»، تفاصيل السجل/تعديله، سجل أرقام الدوائر وسياق صفه). الموظفون ~8. إعدادات المؤسسة ~10: المجموعات الأربع (بيانات المؤسسة / الديوان المركزي / الترقيم / الجهة المسؤولة)، «حفظ الإعدادات»، وشرح **الحالة المعطَّلة** الفريدة في `EmployeePicker` (هنا وحده يُشرح سبب التعطيل لأنه مرئي).
**قبول:** كما سبق؛ مع فحص خاص أن شرح الحقول في نموذج إعدادات المؤسسة يطابق `Section`اتها.

### Phase 6 — `/audit` و `/` (لوحة التحكم) ثم الإغلاق

**نطاق:** التدقيق ~10 (لوحتا السجل/تقارير السلامة، مرشحات الوحدة/الإجراء/المدى الزمني، «فحص السلامة»، «إعادة فحص هذا النطاق»، البنود المشروطة بصلاحية إدارة التدقيق). لوحة التحكم ~4 (بطاقات المؤشرات، «ما التالي؟»، شارة النسخة الأولية).
**الإغلاق:** مراجعة نهائية للمحتوى العربي (تكرار/تناقض/طول)، مصفوفة الأدوار على المسارات الأحد عشر، تشغيل `check:guides` وإصلاح اليتامى، البوابات الأربع، وصفحة «الوضع التعليمي» في READMEs: ما هو، كيف يُشغَّل/يُطفأ، وكيف يُضاف مدخل جديد لصفحة.

## 5. خارج النطاق صراحةً

- أي مكتبة جولات أو tooltip/popover جديدة، وأي حزمة npm غير موجودة.
- Spotlight/تعتيم الشاشة، والإبراز المستند إلى إحداثيات، والتمرير التلقائي للعنصر المشروح.
- شرح `/login` و`/change-password`: خارجا `AppShell` فلا سبيل للوصول إلى مفتاح الوضع هناك، و`change-password` الاضطراري يظهر قبل أن يملك المستخدم تفضيلًا. إن طُلب لاحقًا يُعامل كاستثناء بتصميم مستقل.
- جولة تلقائية عند أول دخول، أو عدّاد «الشرح مُطّلع عليه»، أو إكمال مرحلي يُخزَّن في الخادم.
- نسخ نصوص الشرح إلى الخادم أو جدولتها أو ترجمتها (لا طبقة i18n في التطبيق أصلًا).
- تلميح الحقول داخل `title=` أو رسائل الأخطاء — الشرح غرضه التعليمي لا الاستبدال التحقق.
- أي سلوك جديد في الجداول أو النماذج؛ الخاصيتان `guideId` اختياريتان تمامًا ولا تغيّران أي مسار قائم.

## 6. المخاطر والقرارات

| الخطر | المعالجة |
| --- | --- |
| تضخّم النص وتكراره مع READMEs | الكتالوج مصدر وحيد للنص الموجّه للمستخدم، وREADME يبقى مرجع المطوّر؛ لا يُنسخ أحدهما في الآخر، والمراحل تُحدّث README بالإشارة إلى الكتالوج فقط. |
| ضجيج الرقاقات (40+ رقاقة في صفحة الوثيقة) | لا رقاقة إلا داخل `GuideRegion` معلن، والرقاقة ghost صغيرة بجانب العنصر لا عائمة؛ وحوار الصفحة هو المسار الأساسي للقراءة. إن ازدحم، تُدمج المناطق المتجاورة في منطقة واحدة. |
| محتوى يصف وظيفة لا يملكها المستخدم | §3.5: الرقاقة تُرسم داخل نفس شرط العرض؛ ومصفوفة الأدوار بوابة إلزامية في كل مرحلة. |
| انزلاق المعرّفات مع إعادة تسمية الواجهات | `check:guides` يفحص المعرّفات اليتيمة والمجهولة، وهو بوابة في كل مرحلة. |
| مساس DOM الإنتاجي (يهدر سنوات من ثبات الواجهة) | التحقق من تطابق `outerHTML` في الوضع المتوقف (معايير Phase 0)، والـ wrapper بلا طابع مرئي. |
| تصادم مع أزرار قائمة الصدفة/السياق | لا رقائق داخل قوائم Radix (لا معنى لزر يفتح حوارًا داخل قائمة): الشرح يُكتب للمناطق والحقول والأزرار العلوية فقط. |
| تكلفة التحقق البشري لكل مرحلة | كل مرحلة تُغلق بصفحة واحدة أو اثنتين فقط، والتحقق يحتاج دخول المستخدم يدويًا؛ تُدرج الملاحظات في سجل هذا الملف كما في Module 06. |
| تعطيل خيط `motion`/`density` القائم | إضافة حقل رابع بنفس نمط الحقول الثلاثة؛ لا إعادة هيكلة لحالة `AppShell`. |

## 7. تسلسل التنفيذ

1. **عند اعتماد هذه الخطة**: Phase 0 كاملة (تفضيل + primitives + كتالوج مشترك + صفحة المستخدمين شاهدًا) → بوابات → توثيق → **توقف للمراجعة**.
2. ثم صفحة-صفحة بالترتيب: Phase 1 → 2 → 3 → 4 → 5 → 6، وكل مرحلة تتوقف عند نهايتها لعرض النتيجة في المتصفح وتحديث السجلات.
3. لا commit لأي مرحلة قبل طلب ذلك صراحةً؛ يُذكر رقم الـ commit في سجل المرحلة عند إنشائه.
4. في كل مرحلة تُشغَّل البوابات: `npm run lint`، `npm run build`، `npm run check:guides`، و`dotnet build` + `dotnet test` (بعد إيقاف خادم 5028 مؤقتًا وإعادته)، رغم أن النطاق front-only — التزامًا بقاعدة البوابات الأربع.
5. التحقق البصري لكل مرحلة يحتاج المستخدم في المتصفح (5173)؛ لا تُكتب بيانات اعتماد في أي سكربت أو ملف.
6. تُحدَّث memory المشروع بنهاية كل مرحلة (الملف: `project-frontend-ux-polish.md` أو سجل مستقل للوضع التعليمي).
