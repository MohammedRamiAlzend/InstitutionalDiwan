## 1. الهدف

1. صفحة إدارة لمخطط الحقول ونسخه لكل نوع وثيقة (`LOOKUP_MANAGE`).
2. نموذج ديناميكي يتولّد من المخطط المنشور عند إنشاء وثيقة/مسودة.
3. عرض وتعديل قيم الحقول في تفاصيل الوثيقة (تعديل في المسودة فقط).
4. أخطاء `DocumentFields.*` بالعربية، ودليل الوضع التعليمي للصفحات الجديدة.

خارج النطاق: فلترة السجل بالحقول الديناميكية (مؤجلة في الـ backend)، وإدارة الـ lookups العامة.

## 2. المسارات (لا endpoint جديد)

| الاستخدام | المسار | الصلاحية |
| --- | --- | --- |
| قائمة/تعريف حقل | `GET`/`POST /api/document-types/{typeId}/fields` | `LOOKUP_MANAGE` |
| النسخ: السجل / بدء مسودة | `GET`/`POST /api/document-types/{typeId}/schema-versions` | `LOOKUP_MANAGE` |
| تفاصيل نسخة / حذف مسودة | `GET`/`DELETE /api/schema-versions/{id}` | `LOOKUP_MANAGE` |
| إضافة/تعديل/إزالة حقل من مسودة | `POST /api/schema-versions/{id}/fields`، `PUT`/`DELETE .../fields/{fieldId}` | `LOOKUP_MANAGE` |
| نشر | `POST /api/schema-versions/{id}/publish` | `LOOKUP_MANAGE` |
| مخطط النوع المنشور | `GET /api/document-types/{typeId}/schema` | `DOCUMENT_VIEW` |
| مخطط الوثيقة + قيمها | `GET /api/documents/{id}/fields` | `DOCUMENT_VIEW` + VIEW |
| تعديل قيم مسودة | `PUT /api/documents/{id}/fields` | `DOCUMENT_EDIT` + DOWNLOAD |
| إنشاء مع القيم | `POST /api/documents`، `POST /api/documents/drafts` (`fieldValues`) | كما هو |

الأنواع: 1 نص، 2 نص طويل، 3 رقم، 4 تاريخ، 5 نعم/لا، 6 قائمة. القيم تُرسل نصًّا: الأرقام invariant، التواريخ ISO 8601، المنطقي `true`/`false`، القائمة بمفتاح الخيار، والفراغ يمسح القيمة.

## 3. البنية (FSD)

| الطبقة | الشريحة | المحتوى |
| --- | --- | --- |
| entities | `document-schema` | قراءات: حقول النوع، سجل النسخ، تفاصيل نسخة، مخطط النوع، مخطط الوثيقة؛ `schemaKeys`؛ الأنواع؛ ثوابت `DataType` ووسوم عربية؛ `FieldTypeBadge`، `SchemaStatusBadge`. |
| features | `document-schema-manage` | كتابة: تعريف حقل، بدء مسودة، إضافة/تعديل/إزالة حقل، حذف مسودة، نشر. Zod لإعدادات الحقل (regex ≤ 500 مع رسالة إجبارية معه، خيارات ≤ 100، ≤ 50 حقلًا). |
| features | `document-field-values` | `DynamicFieldsForm` (مولِّد حقول من المخطط) + `useSetDocumentFieldValues`. يُستخدم من الإنشاء والتفاصيل. |
| widgets | `document-schema-editor` | محرر النسخة: قائمة الحقول، ترتيب العرض، لوحة إعدادات الحقل، شريط النسخ (مسودة/منشورة/متقاعدة). |
| widgets | `document-fields-panel` | تبويب «الحقول» في تفاصيل الوثيقة (قراءة، وتعديل عند المسودة). |
| pages | `document-schemas` | مسار `/document-schemas` بصلاحية `LOOKUP_MANAGE`، ≤ 120 سطرًا. |

تعديلات على موجود: `features/document-create` (يضيف `DynamicFieldsForm` بعد اختيار النوع)، وصفحة التفاصيل (تبويب جديد)، والـ sidebar (عنصر «مخططات الحقول»).

## 4. قرارات التصميم

1. **اختيار نوع الوثيقة** في صفحة المخطط عبر قائمة الأنواع الحالية من `entities/lookup`؛ لا إدارة lookups عامة.
2. **المحرر يعمل على المسودة فقط.** النسخة المنشورة/المتقاعدة للقراءة مع زر «إنشاء مسودة جديدة منها» (الـ backend يسمح بمسودة واحدة لكل نوع، فيُعطَّل الزر ويُشرح السبب إن وُجدت).
3. **تحديد الحقل**: `key` و`dataType` يُدخلان عند الإنشاء ثم يُقفلان في الواجهة (الـ backend يمنع تغييرهما). لا حذف لحقل، فقط إزالته من المسودة.
4. **النشر** يمرّ بحوار تأكيد يشرح أن النسخة تتجمّد ولا تتأثر الوثائق الموجودة.
5. **تغيير النوع في فورم الإنشاء** يعيد جلب المخطط ويفرّغ القيم الديناميكية (مع تنبيه إن كانت معبّأة).
6. **عرض المنطقي والتواريخ**: المفاتيح والقيم اللاتينية والأرقام في جزر `dir="ltr"`، وفق قاعدة RTL في CLAUDE.md.
7. **الأخطاء عند الحقل**: `DocumentFields.ValueRequired/ValueTypeInvalid/ValueTooLong/ValueBelowMinimum/ValueAboveMaximum/UnknownField` تحمل مفتاح الحقل في الـ detail الإنجليزي؛ الواجهة تفحص الحقول محليًا قبل الإرسال أولًا (إجباري، نوع، حدود، regex بنفس رسالة المدير)، وما يمرّ إلى الخادم يُعرض كخطأ عام بالعربية على النموذج. التحقق من إمكانية ربط الخطأ بحقل محدد يتم في المرحلة 0 (نقطة مفتوحة 1).

## 5. المراحل

### المرحلة 0 — الأساس
- `entities/document-schema` كاملة (أنواع تطابق `DocumentFieldResponses`، مفاتيح، hooks، شارات).
- إضافة كتالوج `DocumentFields.*` العربي (≈ 45 رمزًا بدءًا من `DomainErrors.DocumentFields`) في `shared/api/errorMessages.ts`.
- فحص: هل يحمل `ProblemDetails` مفتاح الحقل بشكل مهيكل أم في النص فقط؟ يُحسم به البند 7.
- تحديث README للشرائح، و`knowledge.md` (إزالة وسم «backend only» تدريجيًا مع كل مرحلة).

### المرحلة 1 — صفحة المخطط (قراءة)
- `/document-schemas` + عنصر sidebar + route guard لـ `LOOKUP_MANAGE`؛ اختيار النوع من URL (`?type=`).
- `widgets/document-schema-editor` للقراءة: سجل النسخ، قائمة حقول النسخة المحددة (`?version=`) على `DataTable` المشترك مع قائمة سياق وأعمدة قابلة للاختيار (`tableId` ثابت `document-schema-fields`).
- Mermaid غير مطلوب هنا.

### المرحلة 2 — الكتابة
- `features/document-schema-manage`: تعريف حقل جديد، بدء مسودة (نسخة من المنشورة)، إضافة حقل إلى المسودة، تعديل إعداداته حسب النوع (regex+رسالة، حد أدنى/أقصى، طول أقصى، خيارات)، إزالة، حذف المسودة، نشر مع تأكيد.
- إخفاء الإجراءات كلها بدون `LOOKUP_MANAGE`، وتعطيلها خارج حالة المسودة.
- إبطال `schemaKeys` بعد كل كتابة؛ نشر نسخة يبطل مخطط النوع أيضًا.

### المرحلة 3 — النموذج الديناميكي
- `DynamicFieldsForm` يولّد: نص، نص طويل، رقم (حدود)، تاريخ، نعم/لا، قائمة اختيار؛ ترتيب بـ `displayOrder`؛ علامة إجباري.
- دمجه في `document-create` للنوعين (مسودة ومسجّلة) وإرسال `fieldValues`.
- حالة «النوع بلا مخطط منشور»: لا يظهر قسم الحقول.

### المرحلة 4 — تفاصيل الوثيقة
- تبويب «الحقول» في `/documents/:id`: عرض القيم مع اسم النسخة المثبّتة ورقمها؛ زر تعديل يظهر فقط للمسودة مع `DOCUMENT_EDIT`؛ للوثيقة المسجّلة/الملغاة قراءة فقط مع توضيح سبب القفل.
- إخفاء التبويب عند عدم وجود مخطط للوثيقة (`SchemaVersionId = null`).

### المرحلة 5 — التحقق والأدلة
- أدلة الوضع التعليمي (`shared/config/guides/`): صفحة المخطط، محرر الحقل، نشر النسخة، تبويب الحقول؛ ثم `npm run check:guides`.
- `npm run build` و`npm run lint` نظيفان.
- تجربة على الـ API الحي بثلاثة أدوار (admin، `USER`، قراءة فقط): إنشاء حقل من كل نوع، نشر v1، إنشاء وثيقة، نشر v2 مع حقل إجباري جديد وبقاء الوثيقة القديمة على v1، تعديل قيم المسودة، قفلها عند التسجيل، رفض regex/حدود، ورفض `403` للأدوار غير المخوّلة. تُترك وثيقة fixture دائمة في قاعدة التطوير.
- تحديث README الجذر وجدول الـ Module 03، وتسجيل الصف في Change Log.

## 6. نقاط مفتوحة

1. ربط خطأ القيمة بحقل محدد (انظر المرحلة 0). الافتراض: التحقق المحلي يغطي الحالة الشائعة، والخادم يظل المرجع.
2. هل تُسمح إعادة ترتيب `displayOrder` بالسحب؟ الافتراض: حقل رقمي بسيط في الإصدار الأول.
3. هل تُعرض النسخ المتقاعدة لغير المدير؟ الافتراض: لا؛ المدير فقط عبر الصفحة، والوثيقة تعرض نسختها المثبّتة عبر `/documents/{id}/fields`.
4. فلترة السجل بالحقول: تنتظر قرار الـ backend (§7.3 في خطته) ولا تدخل هنا.

## 7. ما اختلف عن الخطة (2026-11-03)

1. `features/document-field-values` اقتصرت على الحفظ (`PUT`) ونموذج التعديل. المولِّد `DynamicFieldInputs` ودوال التحقق (`validateFieldValues` وغيرها) انتقلت إلى `entities/document-schema` لأن FSD يمنع `features/document-create` من استيراد feature شقيقة.
2. بند §6.1: جسم الخطأ لا يحمل مفتاح الحقل بشكل مهيكل (`code` + `detail` إنجليزي فقط)، فالتحقق المحلي هو الطريق الأساسي لإظهار الخطأ عند الحقل، وما يصل من الخادم يظهر رسالة عربية عامة على النموذج.
3. بند §6.2: ترتيب العرض حقل رقمي بسيط (لا سحب).
4. بند §6.3: النسخ المتقاعدة لا تُعرض إلا في صفحة المخطط للمدير.
5. الأرقام تعود من الـ API بكسور ثابتة (`500.00000000`)؛ تُعرض وتُحرَّر بدونها عبر `normalizeNumberText`.
6. جُرّبت لاحقًا في المتصفح (2026-11-03): تعديل حقل وإزالته وحذف المسودة، وقفل القيم بعد التسجيل (واجهة بلا زر تعديل مع سبب القفل، والخادم يردّ 409 `Correspondence.OnlyDraftEditable`). كشف الاختبار خللًا: حوار تعديل الحقل كان يفتح فارغًا لأن النموذج يُبنى قبل اختيار الحقل؛ أُصلح بتركيب الحوار لكل هدف (`key`).
